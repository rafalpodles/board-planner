Part B is complete: all ten tasks implemented, every one independently reviewed, every review folded

## The governing idea, in one line

**The server may say what work exists and stop it; the laptop decides where anything runs.** A
repository path is a capability the operator grants locally (`repos.json`), never something the
server can set. Everything below follows from that.

## Decisions waiting on rpo

**1. CP-195 / finding C4 — the enrolment token. This is the one that matters.**
`POST /api/workers/register` is `withAdmin`, so the token on the laptop must belong to an instance
admin. The agent runs with `--permission-mode bypassPermissions` and `Read`, at the same uid, and the
token's path is documented in the repository it is editing. It can read that token and `PATCH
/api/workers/:id` to clear `lockedByInstance` — **a kill switch the killed process can switch off.**
This blocks running the worker unattended against a real repository. Two shapes were discussed: a
one-time enrolment credential, or manual registration in the console with the credential copied
across. rpo parked the choice.

**2. Whether to merge this branch.** 103 commits. Another session writes to `main` regularly and has
already, today, checked its own branch out *inside this worktree* and deleted `worker/` from disk.
Coordinate before merging.

## Deliberately not done — separate work, not gaps

- **A worker killed mid-run leaves its phase up to 2h.** `releaseExpiredTasks` has exactly one caller,
  the claim route, so nothing sweeps a project no worker is polling. The panel makes this visible
  (the dot goes amber after five minutes of silence); the real fix is a sweeper.
- **The fleet console has no quiet-run treatment**, unlike the task panel. Same principle, not applied.
- **No UI for policy fields.** `model`, `reviewModel`, `maxDiffLines` and the rest are API-only —
  true before this branch as well.
- **Changing a column's role** leaves phases on tasks that are no longer in an active column.
- `workerId` renders as a raw ObjectId on the task panel; the fleet console shows name and host.

## What live verification proved, and the one bug it found

Rig: MongoDB 4.4.30 on 27017 (database `cp161_live`), the branch's own build, a scratch git repo with
a bare origin and an integration clone, and a stubbed `gh` that really merges.

Confirmed end to end: the socket returns real telemetry at mode 0600 (`agent`, tool `Read` with a
path, history `claiming → worktree → agent`); the phase reaches the task and is cleared on exit; the
API sends only `workerId`/`phase`/`phaseAt`/`startedAt`/`asOf`; the fleet console shows `CP-1
gates:review`; and the agent's work really landed on `origin/main`.

**The bug it found was mine, from the same day.** A review had noted a claimed task shows no panel
until its first telemetry event, so I began rendering whenever `workerId` was present. But `workerId`
and `startedAt` are left behind as history — only the phase trio and `runId` are cleared — so every
finished task then rendered `starting · running 3m` forever. Fixed in `b9e545c` by keying the
serializer on `runId`. **No test and no review caught this; only a running system did.**

Separately, the first live run reached `done` without the merge landing — that was the **rig** lying,
not the product: the `gh` stub answered `MERGED` unconditionally, and the worker's merge-state
recovery path honestly believed it. The stub now reports the real state.

## Bringing the rig back up

```bash
# 1. Mongo 4.4 must be listening on 27017 (container `am_test`), database cp161_live
# 2. app, from the worktree:
MONGODB_URI=mongodb://127.0.0.1:27017/cp161_live NEXT_PUBLIC_APP_URL=http://localhost:3991 \
  npx next start -p 3991
# 3. worker, from worker/ after npm run build:
PATH="$HOME/cp-rig/bin:$PATH" CP_API_URL=http://localhost:3991 \
CP_API_TOKEN_FILE=$HOME/cp-rig/token CP_WORKER_NAME=rig-laptop \
CP_STATE_DIR=$HOME/cp-rig/state node dist/main.js
```

Login `rpo` / `rig-pass`. `~/cp-rig/` holds the scratch repo, bare origin, integration clone, the
`gh` stub and the worker state dir. Seed script logic is in the session transcript; the database
survives unless someone drops it.

Gotchas paid for: the scratch repo needs a `package-lock.json` (the build gate runs `npm ci`);
`CP_STATE_DIR` must not sit under `/private/...` (`repos.ts` refuses it); `repos.json` is
`{"repos":[path]}` at mode 0600 in a 0700 directory; and `preview_start` resolves `launch.json` from
the **main repo**, not this worktree, so it cannot serve this branch's build.

## Working rules this branch earned the hard way

- **Verify a subagent's report from files, never from the report.** One implementer described a
  change that was not in its commit.
- **`git status` after every subagent, especially a failed one.** A review agent killed mid-run left
  its own mutation — scrubbing secrets *after* truncation — sitting in the working tree.
- **Never make a failing test pass by amending its input.** If the test and the implementation
  disagree, the implementation is the suspect. This was violated once and produced a test asserting
  nothing.
- **`worker/tsconfig.json` excludes test files and vitest does not typecheck**, so a missing import
  in a test is invisible: the symbol is `undefined` and an assertion can pass for the wrong reason.
  Bit me personally.
- **`vi.fn()` attaches its own handler to any promise it returns**, so `mockRejectedValue` can never
  prove a fire-and-forget path has its own `.catch()`. Use a plain function.
- **Mocked Mongoose validates no driver options.** An aggregation-pipeline update needs
  `updatePipeline: true` and the mock accepts it without. Exercise pipeline updates against a real
  Mongo.
- Every review on this branch found something real. The three commits that skipped review — because
  a usage limit made one unavailable — turned out to be the weakest code here, and all three tests
  the eventual review attacked survived their mutations.
